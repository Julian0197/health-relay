# 原生 SDNN 云端服务

`wrangler.native.jsonc` 部署独立的 `healthrelay-native` Worker 和 SQLite Durable Object。此入口服务于显式选择 SDNN 的设备任务，不需要群 webhook。设备负责 HealthKit 读取、增量游标、认证和待传重试；明细存储、计算、签名和看板发布都在 Cloudflare。既有客户端 RMSSD 预设、本地 `native-store.mjs` 接收器及心率明细支持保持原有行为；SDNN 云端服务使用单独的仓储和 Node SQLite 测试适配器。

## 协议与固定起点

设备使用 `POST /ingest`、`X-Acceptance-Key` 和 `Idempotency-Key` 上传原生 `schemaVersion: 1` JSON。明细、删除事件及回执同事务提交；客户端收到匹配批次的 `committed: true` 才推进游标。相同批次返回原回执，正文改变返回 409，校验失败整批不提交。

云端的 `NATIVE_MIN_START` 拒收起点之前的新增记录，不能代替设备侧的同步起点。若客户端已支持固定起点，可设置 `range.start` 为固定 ISO 时间，例如 `2026-10-26T00:00:00+08:00`；该客户端能力属于独立变更，不包含在本次服务端 MR 中。未支持固定起点的客户端需先核对首次回溯范围与服务端下限，避免回溯数据被拒收或一次性补传耗尽额度。切换时创建显式采集 SDNN 的新任务 ID 和同步状态，停用并保留旧任务，不能复制旧任务的待传批次。

## 历史补传

需要补充评分基线时，先将云端 `NATIVE_MIN_START` 调整到允许的历史起点，再使用 App 的“历史补传”读取固定时间范围。补传沿用原任务的指标和接口，使用独立的进度、批次和回执，不修改日常增量任务的游标。大范围会分批继续，全部确认后标记完成；重复记录由云端去重。数据来自设备 HealthKit，不导入旧 Mac 数据库或旧评分结果。

## 部署

在 `integrations/hae-webhook` 使用 Node 22：

```sh
npm ci
npm test
npm run test:native
npm run test:native-budget
npm run check:native
```

使用当前账号的免费方案。将 `wrangler.native.jsonc` 复制到忽略的私有配置中，配置正确的 `main` 路径及账号；签名准备好后设置 `SIGNATURE_ENABLED=true`。通过 Wrangler Secrets 保存以下绑定，不能写入公开配置或浏览器页面：

| 绑定 | 用途 |
| --- | --- |
| `NATIVE_API_KEY` / `NATIVE_MIN_START` | 上传认证 / 固定采集下限 |
| `FEISHU_APP_ID` / `FEISHU_APP_SECRET` | 飞书应用身份；租户令牌在服务端缓存并按需刷新 |
| `SIGNATURE_BASE_TOKEN` / `SIGNATURE_TABLE_ID` / `SIGNATURE_RECORD_ID` | 现有签名固定记录，文本字段 `title` |
| `DASHBOARD_CACHE_BASE_TOKEN` / `DASHBOARD_CACHE_TABLE_ID` / `DASHBOARD_CACHE_RECORD_ID` | 独立展示 Base 的固定记录，文本字段 `payload_24h`、`payload_7d`、`generated_at` |

写入应用需要两个指定 Base 的编辑权限。妙笔读取应用只需展示 Base 的只读权限。HTMLBox 的发布副本包含展示数据读取能力，必须保持私有；不包含上传密钥或应用 Secret。构建与发布见 [看板说明](../integrations/hae-webhook/dashboard-app/README.md)。

```sh
npx wrangler deploy --config /absolute/private/wrangler.production.jsonc
npx wrangler secret bulk /absolute/private/worker-secrets.json --config /absolute/private/wrangler.production.jsonc
```

`GET /healthz` 仅证明 Worker 响应。`GET /status`、`GET /dashboard?range=24h`（或 `7d`）、`POST /signature/refresh`、`POST /dashboard-cache/refresh` 均需上传认证。诊断接口不能提供给看板读者。

## 计算与调度

`NativeRepository` 保留明细和回执，按北京时间分日建立索引及缓存，只向评分提供最近 35 天数据。数据变化后合并发布，指标过期、24h / 7d 展示边界及北京时间跨日触发 Alarm；失败持久化并退避重试。签名和看板使用同一次计算及活动汇总。签名写入后读回核对，重复 Alarm 不重复发布相同标题；发布期间到达的新批次保留待发布状态。

每日缓存保存完整记录，超过 1 MB 的日期使用事务提交的 512 KiB UTF-8 字节块。版本化快照配合按日期索引的变更日志：新增、更正、删除及跨日移动只追加相应变更，并与明细、批次回执同事务提交；重启后组合快照与增量，不再因为一条新记录而重读整天。单日增量达到 256 KiB 或 16 个块后合并快照。旧版写入器的批次计数发生变化时，仅重建派生缓存，原始记录和回执保留。

进程内按日期维护紧凑指标投影，步数与能量等累计指标更新总和，均值指标维护总和与样本数；更正和删除反向更新，移除分组首条或时间极值时只修复受影响分组。精确 HRV、心率及睡眠区间继续用于评分。评分结果按相关数据修订及已发布趋势复用，步数/能量变化不会重复评分；未来样本生效、状态过期、历史窗口边界及北京时间跨日会使复用失效。

图表心率与 HRV 明细按 24h / 7d 窗口筛选，评分仍保留所需历史，睡眠历史基线、30 天锻炼心率和全局通道统计保持原有语义。发布前固定活动快照，避免发布期间的新上传让同一份展示混用不同批次。状态查询不构建图表。

首批数据保留约 30 秒的合并等待，后续连续上传按最近一次计算合并为最多每 5 分钟一轮。普通 24h / 7d 窗口滚动合并到 15 分钟边界；健康状态过期、保留状态到期及北京时间零点仍按准确时间复核。未到任何待办时的 Alarm 直接返回；新上传不会延后已经到期的 Alarm。手动刷新仍可立即请求计算。

Cloudflare Alarm 的自动失败重试次数有限，长期额度或存储故障后需要再次调用 `setAlarm` 才能恢复。新增上传和已提交批次的重试都会重新挂起已经过期至少 5 分钟的旧闹钟；短暂超时的闹钟继续保留原定时间，避免持续上传推迟健康队列。受保护的 `/status` 同时返回 `scheduledAlarmAt` 和逻辑任务的 `dueAt`，便于区分平台闹钟与待发布状态。平台行为见 [Alarm 官方说明](https://developers.cloudflare.com/durable-objects/api/alarms/)。

数据库免费读取或写入额度耗尽时，受保护接口返回 HTTP 503 和明确的限额错误，并通过 `Retry-After` 指向下一次 UTC 零点。设备保留原批次并使用现有重试机制；重签名或重新部署不会重置已经消耗的账号额度。

展示快照按 JSON 转义后的文本大小控制单元格预算，必要时进一步合并心率图表点，保留区间最小值、最大值和缺测间隔；原始明细与评分输入不受影响。发布后重新读取记录校验两个窗口，不能仅凭更新接口回显判断成功。

从空库启动后，基线不足时显示数据积累中或暂无，不能用旧库结果补足。长期明细保留策略没有在此次调整。

## 验收与回滚

先验证隔离环境中的事务失败、重复上传、正文冲突、删除、重启回执、Alarm 重试及 35 天读取预算。再核对真机回执、云端计数、两个 Base、实际签名与 HTMLBox 的 24h / 7d，最后停止 Mac LaunchAgent 后再次上传。未完成这些步骤不能仅凭构建或 `/healthz` 声称迁移成功。

回滚时先关闭云端发布，停用云端设备任务，再恢复旧任务及 Mac 服务。保留原 SQLite 和任务备份，不将旧库导入云端。
